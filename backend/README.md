# Network Documentation Backend

FastAPI + PostgreSQL. Модель данных:
`device_types → device_templates → devices → interfaces → links`

- **device_types** — категория устройства (Коммутатор, Сервер...), задаёт
  префикс для автогенерации кода устройства.
- **device_templates** — шаблон/модель техники (например "Cisco Catalyst
  2960-24TT"): категория + набор портов. Заводится один раз для модели.
- **devices** — устройство в спецификации оборудования, экземпляр шаблона.
  `code` генерируется автоматически (SW-0001, SRV-0002...), `name`
  необязательно.
- **interfaces** — порты устройства, копируются из шаблона при создании
  устройства; статус порта (свободен/подключён) нигде не хранится —
  вычисляется по наличию связи в `links`.
- **links** — связь напрямую между двумя интерфейсами, без привязки к
  «только коммутаторам». `template_id` необязателен: быстрое подключение
  порта создаёт связь без шаблона, назначить его можно потом.
- **link_templates** — пресет связи: среда передачи + категория кабеля +
  оформление на топологии (цвет, стиль линии). Длина и разъём — свойства
  конкретного отрезка кабеля, поэтому остаются на самой связи.
- **tags** — вложенные теги для группировки устройств (пришли на замену
  площадкам): у тега может быть родитель (`parent_id`), а у устройства —
  сразу несколько тегов. Вложенность — для организации списка тегов
  (например «Завод → Цех 1 → Шкаф А» как путь), фильтрация по тегу ищет
  точное совпадение, без автоматического захвата дочерних тегов.
- **topology_groups** — отдельный от тегов параметр кластеризации на схеме
  связей: ровно одна группа на устройство (`devices.topology_group_id`,
  `ON DELETE SET NULL`), только имя и цвет. Нужен отдельно от тегов, потому
  что тег многозначен/вложен, а рамка-контейнер на схеме требует ровно
  одного родителя на узел. `devices.topology_x`/`topology_y` — координаты
  узла на схеме, сохраняются при перетаскивании (`PATCH
  /devices/{id}/position`), чтобы раскладка не пересчитывалась заново при
  каждом открытии страницы.

## Запуск

Весь стек (база, API, интерфейс) поднимается одной командой из корня
репозитория — см. [README проекта](../README.md). Единственный
`docker-compose.yml` лежит там же.

Только база и API, без интерфейса — когда фронтенд гоняется локально через
`npm run dev`:

```bash
cd ..            # в корень репозитория
docker compose up -d db backend
```

API поднимется на `http://localhost:8000`, Swagger UI — на
`http://localhost:8000/docs`.

При первом запуске автоматически:
- накатываются миграции (схема создаётся с нуля или дообновляется — см. ниже),
- заполняется справочник типов устройств (с префиксами кодов),
- создаётся администратор (логин/пароль — из `.env`, или
  `admin` / `change-me-please` по умолчанию — **смените сразу после первого входа**).

## Запуск локально без Docker

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
export DATABASE_URL=postgresql://netdoc:netdoc@localhost:5432/netdoc
alembic upgrade head          # схему создают миграции, а не приложение
uvicorn app.main:app --reload
```
Потребуется локально поднятый PostgreSQL с базой `netdoc`.

## Миграции

Схему создаёт и меняет Alembic, а не приложение. В контейнере перед стартом
uvicorn выполняется `python -m app.db_upgrade` — он же корректно подхватывает
базы, поднятые ещё старым `create_all` (таблицы есть, истории миграций нет):
такая база помечается штампом `0001_baseline`, после чего накатываются
только последующие ревизии.

```bash
alembic upgrade head            # накатить
alembic downgrade -1            # откатить одну ревизию
alembic revision --autogenerate -m "что сделано"
alembic current                 # какая ревизия применена
```

Адрес базы Alembic берёт из `app.config`, в `alembic.ini` его дублировать не
нужно.

**Источник истины по схеме — миграции.** `schema.sql` остаётся как
человекочитаемое описание модели данных с комментариями; при расхождении
верить нужно `alembic/versions/`.

## Типы данных

Адреса и даты хранятся нативными типами PostgreSQL: `INET` (IP устройства и
порта, шлюз VLAN), `CIDR` (подсеть), `MACADDR`, `DATE`. База сама отвергает
мусор и нормализует запись MAC.

Входные данные проверяются на уровне схем (`app/fields.py`), поэтому кривое
значение возвращает 422 с указанием поля, а не 500 из драйвера. MAC
принимается в любой привычной записи (`A4-BB-6D-11-22-33`, `a4bb.6d11.2233`,
`A4BB6D112233`) и приводится к `a4:bb:6d:11:22:33`. Подсеть вида
`10.10.1.5/24` приводится к адресу сети `10.10.1.0/24`.

## Тесты

```bash
pip install -r requirements-dev.txt
createdb netdoc_test                     # нужен поднятый PostgreSQL
TEST_DATABASE_URL=postgresql://netdoc:netdoc@localhost:5432/netdoc_test pytest -q
ruff check .
```

Тесты гоняются на настоящем PostgreSQL, а не на SQLite: модели используют
типы, которых в SQLite нет (`ARRAY`, а после перехода на нативные типы —
`INET`/`MACADDR`), и проверять поведение на другом диалекте бессмысленно.
Схема создаётся один раз на прогон, таблицы очищаются перед каждым тестом
(`TRUNCATE ... RESTART IDENTITY`), поэтому коды устройств предсказуемы.

Те же проверки выполняет CI (`.github/workflows/backend.yml`) на каждый
pull request.

## Аутентификация

`POST /auth/login` (form-data: `username`, `password`) → `access_token`.
Далее передавать `Authorization: Bearer <token>`.

**Токен нужен всем эндпоинтам, включая чтение.** Открыты ровно два:
`POST /auth/login` (иначе токен негде взять) и `GET /health` (проба живости
контейнера). Требование навешено на уровне роутеров в `main.py`, а не на
отдельные хендлеры — чтобы новый эндпоинт нельзя было забыть защитить;
тест `tests/test_authorization.py` обходит все маршруты приложения и падает,
если появился незащищённый.

Swagger UI (`/docs`, `/openapi.json`) оставлен открытым осознанно: он
описывает форму API, но не отдаёт данных, а система работает во внутренней
сети. Все запросы из него всё равно требуют токен (кнопка Authorize).

Роли: `admin` (полный доступ + управление пользователями),
`editor` (может создавать/менять устройства, интерфейсы, связи),
`viewer` (только чтение).

## Настройки

Все переменные — в `.env.example`. Конфигурация собрана в `app/config.py`
и в продовом режиме проверяется при старте: с `ENVIRONMENT=production`
приложение **не поднимется**, если `SECRET_KEY` оставлен дефолтным или
короче 32 символов, а `CORS_ORIGINS` пуст или равен `*`. Сообщение в логе
говорит, что именно поправить.

Локальная разработка эти проверки не проходит намеренно: с
`ENVIRONMENT=development` (значение по умолчанию) дефолты работают как
раньше и генерировать ключ ради `docker compose up` не нужно.

## Основные эндпоинты

| Метод | Путь | Описание |
|---|---|---|
| POST | `/auth/login` | вход |
| POST | `/auth/users` | создать пользователя (только admin) |
| GET/POST/PATCH/DELETE | `/tags` | вложенные теги (`parent_id`) для группировки устройств |
| GET/POST/DELETE | `/device-types` | категории устройств (название + префикс кода) |
| GET/POST | `/vlans` | VLAN |
| GET/POST | `/device-templates` | шаблоны устройств (модель + набор портов) |
| GET/PATCH/DELETE | `/device-templates/{id}` | один шаблон |
| POST/DELETE | `/device-templates/{id}/interfaces[/{iface_id}]` | порты шаблона |
| GET/POST | `/devices` | устройства спецификации оборудования (`template_id` обязателен, `code` генерируется сам; `?tag_id=` фильтрует список) |
| GET/PATCH/DELETE | `/devices/{id}` | одно устройство |
| PUT | `/devices/{id}/tags` | заменить набор тегов устройства целиком |
| GET/POST | `/devices/{id}/interfaces` | порты устройства (добавить сверх тех, что пришли из шаблона) |
| PATCH/DELETE | `/interfaces/{id}` | изменить/удалить порт |
| GET/POST | `/links` | связи между портами (создание — напрямую по `interface_a_id`/`interface_b_id`, `template_id` необязателен) |
| PATCH/DELETE | `/links/{id}` | назначить шаблон/разъём/длину или удалить связь |
| GET/POST | `/link-templates` | шаблоны связей (среда + категория кабеля + цвет/стиль для топологии) |
| PATCH/DELETE | `/link-templates/{id}` | изменить/удалить шаблон связи (у связей просто снимется, не удаляются) |
| GET | `/search?query=` | поиск по IP/MAC/имени/коду |
| GET | `/topology` | узлы+рёбра для визуализации схемы (фронтенд теперь строит её сам из уже загруженных данных, эндпоинт остаётся для внешних потребителей API) |
| GET/POST/PATCH/DELETE | `/topology-groups` | группы для кластеризации на схеме связей (имя + цвет, отдельно от тегов) |
| PATCH | `/devices/{id}/position` | сохранить позицию устройства на схеме связей (`x`, `y`) после перетаскивания |

## Пример: задокументировать связь

```bash
# 1. Завести шаблон 24-портового коммутатора (один раз для модели)
POST /device-templates
{
  "name": "Cisco Catalyst 2960-24TT", "device_type_id": 1, "manufacturer": "Cisco",
  "interfaces": [{"label": "Порт 1", "port_number": 1}, {"label": "Порт 2", "port_number": 2}, ...]
}

# 2. (Необязательно) завести теги и добавить реальный коммутатор в
#    спецификацию — code сгенерируется автоматически (SW-0001), порты
#    скопируются из шаблона, теги можно назначить сразу
POST /tags
{ "name": "Цех 1" }
POST /devices
{ "template_id": 1, "name": "Коммутатор цех №1", "management_ip": "10.10.1.2",
  "location": "Шкаф ШК-1", "tag_ids": [1] }

# 3. Завести шаблон станка с одним портом и добавить сам станок
POST /device-templates
{ "name": "ЧПУ Haas VF-2", "device_type_id": 5, "interfaces": [{"label": "eth0"}] }
POST /devices
{ "template_id": 2, "name": "Станок ЧПУ №5" }

# 4. Связать порт коммутатора и порт станка — статус портов пересчитается
#    сам (свободен -> подключён), шаблон связи не обязателен
POST /links
{ "interface_a_id": <id порта SW-0001>, "interface_b_id": <id eth0 станка> }

# 5. При желании завести шаблон связи и присвоить его — тогда на топологии
#    эта связь будет нарисована его цветом и стилем линии
POST /link-templates
{ "name": "Медь Cat6", "media_type": "copper", "cable_category": "cat6", "color": "#3366ff" }
PATCH /links/{id}
{ "template_id": 1, "connector_type": "RJ45", "length_m": 40 }
```

Полное описание схемы БД — в `schema.sql`.
