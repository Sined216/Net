# NetDoc — пробный фронтенд

Одностраничное приложение на чистом JS (без сборки, без npm) поверх API из
`backend/`. Задача — «пощупать» модель данных руками: завести шаблон
устройства, добавить по нему устройство в спецификацию, подключить порт к
порту, посмотреть топологию — и понять, чего не хватает в структуре БД.

## Запуск

1. Поднимите бэкенд (из `backend/`):
   ```bash
   docker compose up -d --build
   ```
   API будет на `http://localhost:8000`.

2. Откройте `frontend/index.html` в браузере — двойным щелчком, либо через
   любой статический сервер, например:
   ```bash
   cd frontend
   python -m http.server 5500
   # http://localhost:5500
   ```
   Оба варианта работают одинаково: бэкенд разрешает запросы с любого источника
   (`CORS_ORIGINS=*`).

3. На экране входа поле «Адрес API» уже указывает на `http://localhost:8000` —
   меняйте, если бэкенд поднят на другом хосте/порту. Логин/пароль по
   умолчанию — `admin` / `change-me-please` (или то, что задано
   в `.env` бэкенда).

## Что внутри

- **Шаблоны** — сначала заводится справочник типов устройств (категория +
  префикс кода, напр. «Коммутатор» → `SW`), затем шаблоны конкретных моделей
  техники (напр. «Cisco Catalyst 2960-24TT») с набором портов. Устройство
  без шаблона завести нельзя — это осознанное ограничение модели. Всё
  редактирование шаблона, включая порты (добавить/удалить, сгенерировать
  N штук), находится внутри кнопки «Изменить»; карточка в списке — только
  просмотр.
- **Устройства** — спецификация оборудования: выбираете шаблон, остальное
  (IP управления, расположение, теги...) необязательно, включая само
  название. Код устройства (`SW-0001`...) генерируется сам, вводить его не
  нужно. Порты копируются из шаблона автоматически; их всё ещё можно
  донастроить (IP/MAC/VLAN) или добавить/удалить вручную поштучно и пачкой.
  У каждого порта — статус, который нигде не хранится и не редактируется
  руками: если у порта есть связь, показывается «→ устройство · порт»,
  иначе «свободен». Подключение порта делается тут же, в его строке —
  выпадающий список сгруппирован по устройствам (устройство → порт),
  показывает только свободные порты; выбрали — сразу «Подключить», связь
  создаётся без отдельной формы и без шаблона (его можно назначить потом).
- **Шаблоны связей** — пресет: среда передачи + категория кабеля + цвет и
  стиль линии для топологии. Длина и разъём в шаблон не входят — это
  свойства конкретного отрезка кабеля, задаются на самой связи.
- **Связи** — просмотр/редактирование (шаблон, разъём, длина, скорость,
  подтверждённость) и удаление; создаются связи не здесь, а из порта во
  вкладке «Устройства».
- **Топология** — строится из уже загруженных данных (без отдельного
  запроса), раскладка — пружинная модель по связям, а не круг. Узел —
  прямоугольник с портами по нижнему краю (зелёный — подключён, серый —
  свободен), связь идёт от конкретного порта до конкретного порта и
  красится цветом/стилем линии из шаблона связи. Колесо мыши — масштаб,
  перетаскивание фона — сдвиг, кнопка «1:1» — сброс.
- **Теги** — вложенные (напр. «Завод → Цех 1 → Шкаф А» как путь), пришли на
  замену площадкам. У устройства может быть сразу несколько тегов —
  выбираются чекбоксами в форме устройства. Вложенность — только для
  организации списка тегов; фильтр по тегу (в «Устройствах» и «Топологии»)
  ищет точное совпадение, дочерние теги автоматически не подхватывает.
- **Поиск** — по IP/MAC/имени/коду устройства.
- **VLAN, Пользователи** — служебные справочники (VLAN — плоский список
  без привязки к месту; управление пользователями доступно только `admin`).

## Ограничения (это прототип, не финальный UI)

- Раскладка топологии не сохраняется между показами — пересчитывается
  заново при каждом открытии вкладки/смене фильтра тега.
- Нет пагинации — весь список устройств грузится за один раз; при сотнях
  устройств понадобится серверная пагинация/фильтрация.
- Шаблон устройства нельзя сменить после создания записи в спецификации —
  только удалить и завести заново.
- Фильтр по тегу — одиночный `<select>` (один тег за раз), не мультивыбор.

Эти места и стоит держать в уме при решении, что менять в структуре БД —
если, например, окажется, что устройств будут сотни, потребуется серверная
пагинация/фильтрация, а не только клиентский фильтр.
