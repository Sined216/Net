## Критичное

### 1. CI сейчас красный — линтер валит сборку

```
app/routers/devices.py:8:25: F401 `app.codegen.next_device_code` imported but unused
Found 1 error.   (exit code 1)
```

Шаг `ruff` в `.github/workflows/backend.yml` падает, а с ним и весь job
`backend`. Импорт был нужен старому коду и осиротел при переносе генерации кода
в `provisioning`. Лечится удалением одной строки (`ruff check --fix .`).

### 2. Поиск не находит того, что ищут чаще всего — проверено

Страница называется «Поиск по IP / MAC / имени». Запрос строится
INNER JOIN'ом от `interfaces` к `devices` и смотрит только на
`Interface.ip`, `Interface.mac`, `Device.name`, `Device.code`
(`app/routers/interfaces.py:209-225`). Отсюда три отказа:

| Запрос | Найдено | А на самом деле |
|---|---|---|
| `10.10.10.20` — IP управления SW-0001 | **0** | устройство есть, список устройств его находит |
| `a4:bb:6d:00:00:00` — MAC устройства | **0** | тот же адрес виден в колонке MAC списка |
| `CAM-0001` — устройство без портов | **0** | устройство есть в спецификации |
| `SW-0001` | **24 строки** | один коммутатор, по строке на каждый порт |

`Device.management_ip` и `Device.mac` в поиске не участвуют вовсе, хотя в
списке устройств по ним есть и колонки, и фильтры. Устройство с нулём портов
(модель без портов — медиаконвертер, ИБП) невидимо для поиска целиком: ни по
коду, ни по имени. А коммутатор, наоборот, забивает выдачу двумя десятками
одинаковых строк — при жёстком лимите в 50 две железки съедают весь ответ.

Чинится заменой INNER JOIN на LEFT OUTER (или UNION с запросом по устройствам),
добавлением `Device.management_ip`/`Device.mac` в условие и схлопыванием
результата до устройства.

### 3. Ниже 768 px меню закрывает собой всю страницу — проверено

`AppShell` объявлен как `navbar={{ width: 220, breakpoint: 'sm' }}` без
`collapsed` (`layout/AppLayout.tsx:76`). По правилам Mantine это значит: на
экране уже `sm` навбар получает `width: 100%`, `offset: 0` и **не** уезжает
трансформацией. Бургера в проекте нет — на его месте пустая заглушка
`<Group … hiddenFrom="sm" />` (строка 137).

Замерено в браузере:

| Ширина окна | Ширина навбара | Что под курсором в центре экрана | Бургеров |
|---|---|---|---|
| 1440 | 220 | текст страницы | 0 |
| 820 | 220 | текст страницы | 0 |
| **767** | **767** | **пункт меню** | **0** |
| **390** | **390** | **пункт меню** | **0** |

То есть на телефоне и в узком окне ноутбука видно только меню, страницы под ним
не достать и закрыть его нечем. Лечится `collapsed: { mobile: !opened }` плюс
`Burger` в то самое пустое место.

### 4. База не может гарантировать «один кабель на порт» — проверено

`links` несёт `UNIQUE(interface_a_id)` и `UNIQUE(interface_b_id)` **по
отдельности** плюс `CHECK (interface_a_id < interface_b_id)`. Этого не хватает:
порт может быть стороной `A` в одной связи и стороной `B` в другой. Проверено
прямым INSERT в базу, поднятую миграциями:

```
link (20,30) inserted
>>> DB ACCEPTED (10,20): port 20 is now in two links
links now: [(1, 20, 30), (2, 10, 20)]
links touching port 20 = 2
```

Комментарий в `models.py` утверждает, что «база теперь это гарантирует», — она
гарантирует лишь отсутствие зеркального дубля той же пары. Единственная
настоящая проверка — `_busy()` в `routers/links.py:12`, а это классический
check-then-act: между `SELECT` и `INSERT` замка нет, и два одновременных
запроса пройдут оба.

Последствие тихое и оттого неприятное: `serialize.build_link_map` кладёт связи
в словарь по `interface_id` (`serialize.py:59`), поэтому у порта с двумя
кабелями останется видимым только последний обработанный — второй кабель
пропадает из интерфейса, продолжая существовать в базе.

Лечится либо отдельной таблицей концов с одним `UNIQUE(interface_id)`, либо
`SELECT … FOR UPDATE` по обоим портам перед вставкой.

### 5. Обязательная смена пароля действует только в браузере — проверено

`must_change_password` проверяет исключительно `AppLayout`, показывая модалку
без крестика. `auth.get_current_user` этот флаг не смотрит вовсе. Значит токен,
выданный по временному паролю, полноценен:

```
petrov must_change_password = True
GET /devices -> 12 devices; first: [('PC-0001','10.10.10.23'), …]
```

Человек, которому администратор продиктовал временный пароль, может годами
работать через API/Swagger, ни разу его не сменив. Это же касается
и `BOOTSTRAP_ADMIN_PASSWORD` из `.env`: README обещает, что «интерфейс
потребует сменить его при первом входе», — API не потребует. Достаточно
отбивать 403 на все маршруты, кроме `/auth/me` и `/auth/me/password`, пока флаг
стоит.

## Существенное

### 6. Оптимистичная блокировка обходится устаревшей формой

`InterfaceRow` инициализирует поля через `useState(iface.ip ?? '')` — начальное
значение берётся один раз при монтировании. Номер правки при этом читается из
живого пропа в момент сохранения: `version: iface.version`
(`devices/InterfaceRow.tsx:60`). Пара «значения — версия» разъезжается:

1. A открыл страницу: порт 5, ip `10.0.0.5`, version 1.
2. B поменял тот же порт на `10.0.0.99` → version 2.
3. A сохранил **другой** порт того же устройства → инвалидируется
   `deviceInterfaces` → рефетч. У строки 5 проп стал version 2 и ip `10.0.0.99`,
   но поля ввода по-прежнему показывают `10.0.0.5`.
4. A нажимает «сохранить» на строке 5 → уходит `version: 2` (свежий) и
   `ip: 10.0.0.5` (устаревший) → сервер сверяет версии, они совпадают, правка B
   молча затёрта.

Ровно тот сценарий, ради которого блокировку и вводили. Лечится захватом версии
вместе со снимком полей (одним `useState({...iface})`) либо синхронизацией
полей с пропом, когда строка не в фокусе.

### 7. `scripts/generate_data.py` не работает — проверено

README предлагает наполнить базу командой
`python -m scripts.generate_data --devices 1000`. Она падает сразу:

```
TypeError: 'location' is an invalid keyword argument for Device
```

`scripts/generate_data.py:128` передаёт `location=…`, а колонку снесла миграция
`0018_drop_location`. Документированный инструмент разработчика сломан;
починка — удалить одну строку.

### 8. VLAN нельзя ни отредактировать, ни увидеть половину введённого

- `PATCH /vlans/{id}` не существует вовсе — только создание и удаление.
  Опечатка в номере или подсети лечится удалением и заведением заново.
- Форма создания собирает **DHCP-диапазон** и **заметки**, а таблица показывает
  только №, название, подсеть и шлюз. Эти два поля не показываются нигде и
  править их нечем — данные уходят в базу навсегда невидимыми.

Для сравнения: у тегов полный набор CRUD с защитой от циклов. VLAN на этом фоне
выглядит недоделанным разделом.

### 9. Поиск — тупик: результат некликабелен

`SearchResult` честно отдаёт `device_id`, но `SearchPage` рисует все четыре
колонки простым текстом. Нашёл железку — и переходи к ней вручную через список.
Строка должна вести на `/devices/{device_id}`, страница для этого уже есть.

### 10. `editor` одной площадки правит справочники всех площадок

Модели техники, разъёмы, модули и шаблоны связей общие для всей системы (так
задумано — «заводить Cisco Catalyst заново на каждой фабрике незачем»), но
пишутся они под правом `EDIT`, без привязки к площадке. Значит редактор
подольского завода может удалить модель или пресет кабеля, на которых держится
документация другой фабрики. Прежний аудит отмечал это только для
`device_types` (пункт D8) — на деле область шире. Логично поднять удаление
общих справочников до `admin`, оставив редактору создание и правку.

### 11. Импорт: файл целиком в память до проверки размера

```python
content = await file.read()          # imports.py:33 — читается ВЕСЬ файл
if len(content) > MAX_BYTES:         # :34 — и только потом проверяется
```

Лимит в 16 МБ отсекает файл уже после того, как он занял память. Плюс
`importer.parse()` — синхронный разбор внутри `async def`, то есть на время
обработки десятитысячной таблицы блокируется весь event loop и остальные
запросы ждут. Права нужны как минимум редакторские, так что это не дыра, а
запас прочности: стоит читать потоком с обрывом на лимите и уносить разбор в
`run_in_threadpool`.

### 12. Развёртывание

- `docker-compose.yml` публикует бэкенд наружу: `"${API_PORT:-8000}:8000"` — по
  умолчанию на всех интерфейсах, вместе со Swagger UI. Интерфейсу этот порт не
  нужен (он ходит через nginx), так что это лишняя мишень для перебора паролей.
  Базу авторы закрыли ровно по этой логике — стоит и здесь либо закомментировать
  проброс, либо привязать к `127.0.0.1`.
- В `nginx.conf` нет ни одного security-заголовка (`X-Content-Type-Options`,
  `X-Frame-Options`, `Referrer-Policy`, CSP).
- HTTPS не предусмотрен нигде, а README прямо зовёт открывать систему по
  `http://<ip>:8080` с других машин: токен и пароль идут по сети открытым
  текстом.
- `bootstrap_admin_password` — единственная настройка, которую
  `Settings._reject_insecure_production_config` не проверяет: дефолт
  `change-me-please` в проде пройдёт молча. В docker-compose переменная
  обязательна (`:?`), так что путь через compose закрыт, — но проверка в
  `config.py` всё равно напрашивается, рядом с `SECRET_KEY` и `CORS_ORIGINS`.

## Чего в продукте нет как класса

Не ошибки, а незакрытые направления — перечисляю, потому что для документирования
заводской сети они заметны:

1. **Экспорт.** Ни спецификации в XLSX, ни кабельного журнала, ни схемы в
   PNG/SVG/PDF. Для передачи подрядчику или в архив это обычно первое, что
   спрашивают.
2. **Пассивная инфраструктура.** Связь строго «порт ↔ порт». Патч-панелей,
   кроссов, розеток нет — линия «коммутатор → патч-панель → розетка → станок»
   документируется только сквозным упрощением.
3. **Стойки и юниты.** Вид группы «шкаф» на схеме есть, но юнитов и позиции в
   стойке нет.
4. **IPAM.** VLAN есть, подсетей, пулов и проверки конфликтов IP нет.
5. **Вложения.** Фото шкафа, паспорт устройства, скан схемы приложить некуда.
6. **Опрос SNMP/LLDP.** Поля `source`, `confirmed`, `last_seen_at`, `speed_mbps`
   заведены под него и пока лежат мёртвым весом.
