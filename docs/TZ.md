## Этап 0. Фундамент — без него нельзя в продуктив

Цель: закрыть дыры, из-за которых систему нельзя показывать за пределами
локальной машины, и получить возможность безопасно менять код дальше.

### 0.1. Закрыть чтение авторизацией `[S1, P0]`

Все эндпоинты, кроме `POST /auth/login` и `GET /health`, требуют валидный
токен.

- Навесить `Depends(get_current_user)` на все GET-хендлеры (или подключить
  роутеры с `dependencies=[Depends(get_current_user)]` в `main.py` — так

**Приёмка:** запрос `GET /devices` без заголовка `Authorization` → 401.
Тест на каждый роутер, что неаутентифицированный запрос отбит.

### 0.2. Управление учётными записями `[S2, P0]`

- `POST /auth/me/password` — смена своего пароля (старый + новый, проверка старого).
- `PATCH /auth/users/{id}` — смена роли и ФИО (только admin).
- `POST /auth/users/{id}/password` — сброс пароля пользователя (только admin).
- `DELETE /auth/users/{id}` — блокировка или удаление (решить: мягкое
  `is_active=false` предпочтительнее — `audit_log.user_id` ссылается на users).
- Запрет удалить/разжаловать последнего admin.
- Политика пароля: минимум 12 символов, проверка при создании и смене.
- 2FA и аудит попыток входа не делаем — система живёт во внутренней сети.
- Экран «Пользователи»: колонка действий, модалка смены пароля, пункт
  «Сменить пароль» в собственном профиле в сайдбаре.
- Флаг `must_change_password` у бутстрап-администратора: до смены пароля
  показывать баннер (или принудительный редирект на смену).

**Приёмка:** после первого входа под дефолтным admin интерфейс требует
сменить пароль; сменённый пароль работает, старый — нет.

### 0.8. Изоляция площадок (разные фабрики)

Требование: схемы разных фабрик не пересекаются никак. Это свойство модели
данных, а не настройка отображения, поэтому задача стоит в фундаменте.

**Почему именно сейчас, а не в этапе 2.** Ключ площадки добавляется в
`devices` и ещё пяток таблиц. Сегодня в базе три устройства — миграция
мгновенная. После импорта тысячи устройств придётся переразмечать их руками,
а сам импорт должен уметь колонку «Площадка» с первого дня. Дешевле сделать
до наполнения.

#### Почему не отдельные базы

Соблазн понятный, но цена высокая: N установок обслуживать, обновлять и
бэкапить по отдельности; справочник моделей техники дублировать в каждой;
сквозного поиска и общего управления пользователями нет вовсе. Изоляцию той
же прочности даёт ключ площадки с ограничениями на уровне PostgreSQL — база
физически не сможет хранить связь между фабриками (см. ниже).

Отдельные установки оправданы в одном случае: если у фабрик разные
администраторы, которые не должны видеть чужие данные даже теоретически, и
разные регламенты обслуживания. Тогда это та же система, развёрнутая
несколько раз, и решение можно принять когда угодно потом — код один и тот же.

#### Что изолируется, а что общее

| По площадкам | Общее на всю систему |
|---|---|
| `devices`, `interfaces`, `links` | `device_types` — категории |
| `topology_groups`, позиции узлов | `device_templates` и их порты — модели техники |
| `tags` — «Цех 1» есть на каждой фабрике | `link_templates` — пресеты кабелей |
| `vlans` — номера у фабрик свои и совпадают | `users` — люди могут работать с несколькими площадками |

Логика деления: описание конкретной сети принадлежит площадке, справочник
моделей техники — общий. Заводить «Cisco Catalyst 2960» заново на каждой
фабрике смысла нет.

**Уникальности переопределяются** там, где раньше были глобальными:
`vlans (site_id, vlan_number)`, `tags (site_id, parent_id, name)`,
`topology_groups (site_id, name)`.

`devices.code` предлагается оставить **глобально уникальным** — общий счётчик,
сквозная нумерация. Так «упал SW-0042» звучит однозначно и сквозной поиск
даёт один ответ. Альтернатива — своя нумерация на каждой площадке, тогда
SW-0001 будет на каждой фабрике; решается одной строкой в генераторе кодов,
но требует явного решения.

#### Гарантия на уровне базы

Проверок в приложении мало: ошибка в одном запросе — и связь уедет между
фабриками. Поэтому изоляция закрепляется составными внешними ключами:

```sql
-- денормализованный site_id + составная уникальность
ALTER TABLE devices    ADD UNIQUE (id, site_id);
ALTER TABLE interfaces ADD COLUMN site_id INT NOT NULL,
                       ADD UNIQUE (id, site_id),
                       ADD FOREIGN KEY (device_id, site_id) REFERENCES devices(id, site_id);
ALTER TABLE links      ADD COLUMN site_id INT NOT NULL,
                       ADD FOREIGN KEY (interface_a_id, site_id) REFERENCES interfaces(id, site_id),
                       ADD FOREIGN KEY (interface_b_id, site_id) REFERENCES interfaces(id, site_id);
```

После этого связь между портами разных площадок нельзя записать в принципе —
не поможет ни ошибка в коде, ни ручной INSERT.

#### Доступ и интерфейс

- Таблица `user_sites(user_id, site_id)` — кому какие площадки доступны;
  роль `admin` видит все.
- Переключатель площадки в шапке; всё приложение работает в контексте
  выбранной. Выбранная площадка — в адресе страницы, чтобы схему можно было
  послать ссылкой.
- Все списки и поиск фильтруются по площадке. Запрос чужого объекта по
  прямому id — 404, а не 403: чужие данные не должны даже подтверждать своё
  существование.

**Приёмка:** пользователь с доступом к одной площадке не видит ни устройств,
ни связей, ни тегов другой ни в списках, ни поиском, ни по прямой ссылке;
попытка создать связь между портами разных площадок отвергается базой (тест
делает это в обход приложения, прямым INSERT).

## Этап 1. Готовность к реальному объёму данных

Цель: система остаётся отзывчивой на целевом объёме — **1000 устройств,
~24 000 портов, порядка 10 000 связей**. Это не запас на будущее: при текущей
архитектуре (всё грузится одним запросом) деградация начнётся уже на
двух-трёх сотнях устройств.

### 1.1. Пагинация и серверная фильтрация `[P1, P2]`

- `GET /devices`: `limit`/`offset` (или cursor), `q` (поиск по code/name/IP),
  сортировка; ответ `{items, total}`.
- Лёгкий режим списка: `DeviceListItem` без вложенных интерфейсов
  (`ports_total`, `ports_connected` числами) — интерфейсы подгружаются
  только для раскрытой карточки через `GET /devices/{id}/interfaces`.
- Аналогично `GET /links` (+ фильтр по устройству), `GET /audit`.
- Фронтенд: перевести фильтры тегов/типов на серверные параметры,
  бесконечная прокрутка или постраничная навигация.

**Приёмка:** страница «Устройства» на целевом объёме (1000 устройств,
24 000 портов) открывается < 1.5 с, первый ответ API < 200 КБ. Проверяется на
сгенерированном наборе данных — скрипт наполнения тестовой базы входит в
объём задачи.

### 1.2. Топология: производительность и стабильность `[P3, P6]`

- Раскладку считать один раз при первой загрузке набора узлов, а не на
  каждое изменение данных; при мутациях — обновлять узлы точечно, не
  перекладывая схему.
- Вынести симуляцию в Web Worker либо ограничить итерации/включить
  Barnes–Hut при n > 100.
- Кнопка «Переразложить» (сбросить сохранённые позиции для видимого набора)
  + `DELETE /devices/{id}/position` или `PATCH` с `null`.
- Решить судьбу `GET /topology`: либо фронтенд переходит на него (тогда
  сервер отдаёт готовые узлы/рёбра и фильтрацию), либо эндпоинт удаляется.
  **Рекомендация:** перейти на серверный `/topology` — он уже отдаёт ровно
  то, что нужно схеме, и снимает необходимость грузить все устройства целиком.
- Фильтры схемы: по тегу (есть), по группе, по типу устройства, скрытие
  неподключённых узлов.

**Приёмка:** 300 узлов / 400 связей — открытие схемы < 2 с, перетаскивание
без лагов, после правки связи схема не «прыгает».

### 1.3. Журнал изменений `[D4]`

- `GET /audit` с фильтрами (сущность, id, пользователь, период) + пагинация,
  только admin (или admin+editor — согласовать).
- Дописать логирование там, где его нет: теги, VLAN, типы устройств,
  шаблоны связей, группы топологии, пользователи, позиции узлов — не логировать.
- Страница «История»: таблица + диф старого/нового значения.
- Блок «последние изменения» в карточке устройства.

**Приёмка:** любое изменение справочника видно в журнале с автором и временем.

### 1.4. RBAC в интерфейсе `[S8]`

- `viewer` не видит кнопок создания/правки/удаления; поля форм — read-only.
- `editor` не видит раздел «Пользователи» (уже так) и системных справочников,
  отданных admin.
- Централизованный хук `useCan('device:edit')` вместо проверок по месту.

**Приёмка:** под `viewer` в интерфейсе нет ни одного действия, приводящего к 403.

### 1.5. Сессии и 401 `[S7]`

- `apiFetch`: 401 → сброс токена, редирект на `/login` с сообщением
  «сессия истекла», без каскада красных тостов.
- Продление токена при активности либо refresh-токен (согласовать: для
  внутренней системы допустимо просто увеличить TTL и корректно обрабатывать
  истечение).

### 1.6. Прочность записи `[D5, D6, E10, P5]`

- Уникальность связи на уровне БД: канонический порядок `a < b` + перекрёстное
  ограничение, чтобы порт не мог оказаться `A` в одной связи и `B` в другой.
- Синхронизация `code_sequences` при старте (`GREATEST(next_value, max(code)+1)`).
- Bulk-создание портов: `POST /devices/{id}/interfaces/bulk` (`{count}` или
  список) одной транзакцией вместо N запросов.
- `InterfaceRow`: сброс локального состояния при изменении входных данных
  (`key` по `updated_at`) либо переход на управляемую форму.
- Оптимистичная блокировка на устройстве, порте и связи — **включена в объём**
  в лёгком варианте: целочисленный `version`, инкремент при каждой записи,
  клиент присылает версию в `PATCH`, при расхождении — 409 и сообщение
  «запись изменена другим пользователем, обновите страницу». Ни блокировок,
  ни автоматического слияния изменений не делаем.

**Приёмка:** два браузера открывают один порт, первый сохраняет — второй при
сохранении получает понятное сообщение вместо тихой перезаписи.

## Этап 2. Функциональность, которой не хватает ежедневно

### 2.1. Экспорт — ~~в объём не входит~~

Исключено решением заказчика. Пункт 3.4 аудита (нет выгрузки спецификации,
кабельного журнала, схемы в PDF) закрывается как «не требуется», а не как
незакрытый долг. Если понадобится позже — вернуть отдельной задачей,
техническое препятствий нет.

### 2.2. Импорт из XLSX/CSV

Основной путь первичного наполнения — через него в систему заедут те самые
1000 устройств. Поэтому раздел проработан подробнее остальных в этапе 2 и
по факту нужен раньше прочего (см. «Порядок работ» ниже).

**Сценарий.** Загрузка файла → сопоставление колонок файла с полями системы
(с запоминанием сопоставления для повторных загрузок) → предпросмотр с
построчной валидацией и подсветкой проблем → применение одной транзакцией
(или ничего, или всё).

**Что импортируем:**
- **Шаблоны устройств** — модель, производитель, категория, список портов.
  Первыми: устройства на них ссылаются.
- **Устройства** — шаблон (по названию), название, IP управления,
  расположение, роль, дата установки, теги, группа на топологии.
  `code` генерируется системой и в файле не участвует.
- **Связи** — устройство A, порт A, устройство B, порт B, шаблон связи,
  разъём, длина. Отдельным файлом, после устройств.

**Разрешение ссылок.** В файле люди пишут названия, а не id: шаблон, теги,
группа, шаблон связи, устройства в связях ищутся по названию/коду.
Ненайденное — ошибка строки с внятным текстом («шаблон "Cisco 2960" не
найден»), а не молчаливый пропуск. Отсутствующие теги по галочке
«создавать недостающие теги» могут заводиться на лету.

**Валидация строк** переиспользует схемы Pydantic из 0.5 — IP, MAC, дата,
перечисления проверяются одинаково и при ручном вводе, и при импорте.

**Отчёт:** создано / обновлено / пропущено, и построчный список ошибок с
номерами строк исходного файла. Отчёт выгружается, чтобы можно было
исправить файл и загрузить повторно.

**Повторная загрузка.** Режим на выбор: «только добавлять» (существующие
пропускать) или «добавлять и обновлять» (сопоставление по коду устройства).
Удаление импортом не делается никогда.

**Приёмка:** файл на 1000 строк с десятком намеренно битых строк —
предпросмотр показывает ровно эти строки с причинами, применение либо
проходит целиком, либо не меняет базу вовсе; повторная загрузка того же
файла в режиме «только добавлять» не создаёт дублей.

### 2.3. Карточка устройства и навигация

- Маршрут `/devices/{id}` — отдельная страница: свойства, порты, связи,
  история, соседи по схеме, кнопка «показать на схеме».
- Глобальный поиск (Ctrl+K) по коду, имени, IP, MAC, серийнику,
  расположению, тегу — с переходом на найденное.
- Расширить `GET /search`: сейчас ищет только по `ip/mac/name/code`,
  добавить заметки, расположение, теги, модель; отдавать тип найденного.

### 2.4. Работа со схемой

- Создание связи перетаскиванием между узлами (`onConnect` → выбор портов
  на обоих концах → `POST /links`).
- Удаление/правка связи по клику на ребро.
- Назначение группы перетаскиванием узла в рамку.
- Легенда (цвета шаблонов связей), автоподбор масштаба под печать.

### 2.5. Изоляция площадок — ПЕРЕНЕСЕНО В ЭТАП 0, см. раздел 0.8

Требование «схемы не пересекаются никак» — это не настройка отображения, а
свойство модели данных, поэтому раздел переехал в фундамент. Причины и
устройство — в разделе 0.8.

### 2.6. Цвет устройства

Сейчас цвет есть у тега, у шаблона связи и у группы на топологии, а у самого
устройства — нет, все узлы схемы одинаковые.

**Цвет задаётся в шаблоне устройства** (`device_templates.color`), то есть на
уровне модели техники: все «Cisco Catalyst 2960» одного цвета, все «ЧПУ Haas
VF-2» — другого. Заводится один раз вместе со шаблоном, красить устройства
поштучно не требуется.

- На схеме цвет уходит в рамку и заголовок узла.
- В списке устройств — в маркер строки.
- Пустое значение — узел рисуется нейтральным, как сейчас.

Переопределение цвета на конкретном устройстве не делаем: до появления
реальной потребности это лишнее поле в форме. Если понадобится — добавляется
позже колонкой `devices.color`, ничего не ломая.

### 2.7. Оформление узлов в стиле Turbo Flow

Turbo Flow — это пример оформления из галереи React Flow (той же библиотеки,
на которой схема уже построена), а не отдельная библиотека: тёмная карточка,
анимированная градиентная рамка, иконка слева, заголовок и подзаголовок.
Переход на него — переписывание `DeviceNode.tsx` и стилей рёбер, модель
данных и логика раскладки не затрагиваются.

Две оговорки, которые стоит учесть до начала:

- оформление рассчитано на тёмный фон; в светлой теме градиентные рамки
  выглядят заметно хуже, так что либо схема всегда тёмная, либо нужен второй
  набор цветов;
- анимированные рамки — это CSS-анимация на каждом узле. На целевых 1000
  устройств их стоит отключать выше какого-то порога, иначе схема начнёт
  подтормаживать на ровном месте.

Хорошо сочетается с 2.6: цвет устройства как раз задаёт градиент рамки.

### 2.8. Вложения

- Файлы на устройстве и на связи: фото шкафа, паспорт, скан схемы.
- Хранение: локальный том или S3-совместимое (согласовать), ограничение
  размера/типов, вирус-скан вне зоны ответственности.

## Порядок работ внутри этапа 0

Предлагаемая последовательность — так, чтобы каждый шаг был проверяемым и
ложился в отдельный обозримый PR:

1. **0.6 (каркас)** — pytest, тестовая база, GitHub Actions. Сначала рельсы,
   потом всё остальное едет по ним, а не вслепую.
2. **0.1 + 0.3** — авторизация чтения и fail-fast по конфигурации. Самое
   срочное и самое компактное по диффу.
3. **0.2** — управление учётными записями (бэкенд + экран).
4. **0.4** — Alembic и сведение `models.py` с `schema.sql`. Самый рискованный
   шаг, поэтому идёт уже при работающих тестах.
5. **0.5** — валидация типов (опирается на настоящие типы Postgres из 0.4).
6. **0.8** — изоляция площадок. Строго до наполнения базы, но не раньше: пока
   идёт отработка функционала и дизайна, ключ площадки ничего не добавляет к
   тому, что нужно увидеть, а работы в нём много.
7. **0.7** — README, удаление прототипа, замена устаревших API.

## Импорт идёт вперёд этапа 1

Формально импорт (2.2) стоит в этапе 2, но по смыслу он нужен раньше:
первичное наполнение — это первое, что произойдёт с системой после запуска,
и до него держать 1000 устройств просто негде. Порядок работ поэтому такой:

**этап 0 (включая изоляцию площадок) → импорт (2.2) → этап 1 → остаток этапа 2 → 3 → 4**

Почему не раньше этапа 0: импорт переиспользует валидацию из 0.5, а она
опирается на настоящие типы Postgres из 0.4. Делать импорт до них — значит
писать проверки дважды.

Импорт обязан идти после изоляции площадок (0.8): в файле должна быть
колонка «Площадка», иначе тысячу загруженных устройств придётся
переразмечать руками.

Побочная выгода: как только импорт готов, приёмочный набор для этапа 1
(1000 устройств, 24 000 портов) генерируется им же, а не отдельным скриптом.
