## Этап 0. Фундамент — без него нельзя в продуктив

Цель: закрыть дыры, из-за которых систему нельзя показывать за пределами
локальной машины, и получить возможность безопасно менять код дальше.

### 0.1. Закрыть чтение авторизацией `[S1, P0]`

Все эндпоинты, кроме `POST /auth/login` и `GET /health`, требуют валидный
токен.

- Навесить `Depends(get_current_user)` на все GET-хендлеры (или подключить
  роутеры с `dependencies=[Depends(get_current_user)]` в `main.py` — так
  надёжнее: новый эндпоинт не забудут защитить).
- `/docs` и `/openapi.json` — закрыть или оставить открытыми осознанно
  (решение зафиксировать в README).

**Приёмка:** запрос `GET /devices` без заголовка `Authorization` → 401.
Тест на каждый роутер, что неаутентифицированный запрос отбит.

### 0.2. Управление учётными записями `[S2, P0]`

- `POST /auth/me/password` — смена своего пароля (старый + новый, проверка старого).
- `PATCH /auth/users/{id}` — смена роли и ФИО (только admin).
- `POST /auth/users/{id}/password` — сброс пароля пользователя (только admin).
- `DELETE /auth/users/{id}` — блокировка или удаление (решить: мягкое
  `is_active=false` предпочтительнее — `audit_log.user_id` ссылается на users).
- Запрет удалить/разжаловать последнего admin.
- Политика пароля: минимум 12 символов, проверка при создании и смене.
- Экран «Пользователи»: колонка действий, модалка смены пароля, пункт
  «Сменить пароль» в собственном профиле в сайдбаре.
- Флаг `must_change_password` у бутстрап-администратора: до смены пароля
  показывать баннер (или принудительный редирект на смену).

**Приёмка:** после первого входа под дефолтным admin интерфейс требует
сменить пароль; сменённый пароль работает, старый — нет.

### 0.3. Fail-fast по конфигурации `[S3, S5, P0]`

- Перевести настройки на `pydantic-settings` (уже в зависимостях, но не
  используется): `Settings(secret_key, database_url, cors_origins, environment, ...)`.
- При `ENVIRONMENT=production` и `secret_key` из списка дефолтных — падать
  на старте с внятным сообщением.
- `CORS_ORIGINS` по умолчанию — список конкретных origin, не `*`;
  `allow_credentials` выставлять только вместе с явным списком.
- `.env.example` дополнить всеми переменными с комментариями.

**Приёмка:** `docker compose up` без `SECRET_KEY` в проде не поднимается,
в dev — поднимается с предупреждением.

### 0.4. Alembic и сведение схемы `[D1, D2, P0]`

- Подключить Alembic, `alembic revision --autogenerate` от текущего состояния
  как baseline.
- **Привести `models.py` к `schema.sql`** (SQL-версия — правильная):
  `INET` для `devices.management_ip`, `interfaces.ip`, `vlans.gateway`;
  `CIDR` для `vlans.subnet`; `MACADDR` для `interfaces.mac`;
  `DATE` для `devices.install_date`; добавить `CHECK (interface_a_id < interface_b_id)`.
  Использовать `sqlalchemy.dialects.postgresql.INET/CIDR/MACADDR`.
- Убрать `create_all()` из старта; в контейнере — `alembic upgrade head` до
  запуска uvicorn.
- Сидирование справочника типов устройств и бутстрап-админа перенести в
  отдельную идемпотентную команду/миграцию данных.
- `schema.sql` оставить как справочную документацию с пометкой, что источник
  истины — миграции (или удалить, чтобы не расходилось второй раз).

**Приёмка:** база, поднятая с нуля миграциями, совпадает по DDL с `schema.sql`
(проверяется тестом-сравнением через `pg_dump --schema-only` или
`alembic check`).

### 0.5. Валидация входных данных `[D3, S9]`

- `IPvAnyAddress` для IP, отдельный валидатор MAC (нормализация в один
  формат), `datetime.date` для `install_date`, `IPvAnyNetwork` для `subnet`.
- `port_type`, `role`, `media_type`, `line_style`, `source` — перевести на
  `Literal`/`Enum` в схемах (сейчас `str` + CHECK только в БД).
- `source` и `confirmed` убрать из `LinkCreate` (выставляются сервером:
  ручное создание → `manual`/`true`; поля остаются под будущий импорт SNMP).
- Ограничения длины на текстовые поля.

**Приёмка:** кривые IP/MAC/дата → 422 с понятным сообщением, не 500.

### 0.6. Тесты и CI `[E1, E2, P0]`

- Backend: `pytest` + `httpx.AsyncClient` + Postgres в CI (services или
  `testcontainers`). Покрыть: авторизацию и роли на каждом роутере,
  генерацию кодов (в т.ч. параллельную), создание/удаление связи и
  пересчёт статуса порта, каскады (удаление устройства/тега/шаблона),
  циклы в тегах, дубликаты label.
- Frontend: `vitest` + Testing Library на утилиты (`flattenTagsOrdered`,
  `tagPath`, `nn*`) и раскладку топологии; smoke-рендер страниц с
  замоканным API.
- GitHub Actions: `ruff` + `mypy` (или хотя бы `ruff`) + `pytest` для
  backend; `tsc -b` + `oxlint` + `vitest` + `vite build` для frontend.
  Обязательные проверки на PR.

**Цель покрытия:** backend ≥ 70 % по строкам, критичные пути (auth, links,
codegen) — 100 %.

### 0.7. Гигиена репозитория `[E5, E6, E7]`

## Этап 1. Готовность к реальному объёму данных

Цель: система остаётся отзывчивой на 500+ устройствах и 10k портов.

### 1.1. Пагинация и серверная фильтрация `[P1, P2]`

- `GET /devices`: `limit`/`offset` (или cursor), `q` (поиск по code/name/IP),
  сортировка; ответ `{items, total}`.
- Лёгкий режим списка: `DeviceListItem` без вложенных интерфейсов
  (`ports_total`, `ports_connected` числами) — интерфейсы подгружаются
  только для раскрытой карточки через `GET /devices/{id}/interfaces`.
- Аналогично `GET /links` (+ фильтр по устройству), `GET /audit`.
- Фронтенд: перевести фильтры тегов/типов на серверные параметры,
  бесконечная прокрутка или постраничная навигация.

**Приёмка:** страница «Устройства» при 1000 устройствах открывается < 1.5 с,
первый ответ API < 200 КБ.

### 1.2. Топология: производительность и стабильность `[P3, P6]`

- Раскладку считать один раз при первой загрузке набора узлов, а не на
  каждое изменение данных; при мутациях — обновлять узлы точечно, не
  перекладывая схему.
- Вынести симуляцию в Web Worker либо ограничить итерации/включить
  Barnes–Hut при n > 100.
- Кнопка «Переразложить» (сбросить сохранённые позиции для видимого набора)
  + `DELETE /devices/{id}/position` или `PATCH` с `null`.
- Решить судьбу `GET /topology`: либо фронтенд переходит на него (тогда
  сервер отдаёт готовые узлы/рёбра и фильтрацию), либо эндпоинт удаляется.
  **Рекомендация:** перейти на серверный `/topology` — он уже отдаёт ровно
  то, что нужно схеме, и снимает необходимость грузить все устройства целиком.
- Фильтры схемы: по тегу (есть), по группе, по типу устройства, скрытие
  неподключённых узлов.

**Приёмка:** 300 узлов / 400 связей — открытие схемы < 2 с, перетаскивание
без лагов, после правки связи схема не «прыгает».

### 1.3. Журнал изменений `[D4]`

- `GET /audit` с фильтрами (сущность, id, пользователь, период) + пагинация,
  только admin (или admin+editor — согласовать).
- Дописать логирование там, где его нет: теги, VLAN, типы устройств,
  шаблоны связей, группы топологии, пользователи, позиции узлов — не логировать.
- Страница «История»: таблица + диф старого/нового значения.
- Блок «последние изменения» в карточке устройства.

**Приёмка:** любое изменение справочника видно в журнале с автором и временем.

### 1.4. RBAC в интерфейсе `[S8]`

- `viewer` не видит кнопок создания/правки/удаления; поля форм — read-only.
- `editor` не видит раздел «Пользователи» (уже так) и системных справочников,
  отданных admin.
- Централизованный хук `useCan('device:edit')` вместо проверок по месту.

**Приёмка:** под `viewer` в интерфейсе нет ни одного действия, приводящего к 403.

### 1.5. Сессии и 401 `[S7]`

- `apiFetch`: 401 → сброс токена, редирект на `/login` с сообщением
  «сессия истекла», без каскада красных тостов.
- Продление токена при активности либо refresh-токен (согласовать: для
  внутренней системы допустимо просто увеличить TTL и корректно обрабатывать
  истечение).

### 1.6. Прочность записи `[D5, D6, E10, P5]`

- Уникальность связи на уровне БД: канонический порядок `a < b` + перекрёстное
  ограничение, чтобы порт не мог оказаться `A` в одной связи и `B` в другой.
- Синхронизация `code_sequences` при старте (`GREATEST(next_value, max(code)+1)`).
- Bulk-создание портов: `POST /devices/{id}/interfaces/bulk` (`{count}` или
  список) одной транзакцией вместо N запросов.
- `InterfaceRow`: сброс локального состояния при изменении входных данных
  (`key` по `updated_at`) либо переход на управляемую форму.
- Оптимистичная блокировка на устройстве и связи (`If-Unmodified-Since`
  или `version`), 409 при конфликте — решить, нужна ли при 2-5 пользователях.

## Этап 2. Функциональность, которой не хватает ежедневно

### 2.1. Экспорт `[раздел 3.4 аудита]`

- Спецификация оборудования → XLSX (код, тип, модель, производитель,
  название, IP, расположение, теги, число портов, дата установки).
- Кабельный журнал → XLSX/CSV (устройство A, порт A, устройство B, порт B,
  среда, категория, разъём, длина, заметки).
- Схема связей → PNG/SVG (экспорт вьюпорта React Flow) и PDF под печать
  A3/A2 с легендой.
- Экспорт уважает текущие фильтры экрана.

**Приёмка:** файл открывается в Excel/LibreOffice без правки, кириллица
не ломается, шапка заморожена.

### 2.2. Импорт

- Импорт устройств из XLSX/CSV: загрузка → маппинг колонок → предпросмотр
  с подсветкой ошибок → применение одной транзакцией.
- Импорт шаблонов устройств (модель + список портов).
- Отчёт об импорте: создано / пропущено / ошибки построчно.

### 2.3. Карточка устройства и навигация

- Маршрут `/devices/{id}` — отдельная страница: свойства, порты, связи,
  история, соседи по схеме, кнопка «показать на схеме».
- Глобальный поиск (Ctrl+K) по коду, имени, IP, MAC, серийнику,
  расположению, тегу — с переходом на найденное.
- Расширить `GET /search`: сейчас ищет только по `ip/mac/name/code`,
  добавить заметки, расположение, теги, модель; отдавать тип найденного.

### 2.4. Работа со схемой

- Создание связи перетаскиванием между узлами (`onConnect` → выбор портов
  на обоих концах → `POST /links`).
- Удаление/правка связи по клику на ребро.
- Назначение группы перетаскиванием узла в рамку.
- Легенда (цвета шаблонов связей), автоподбор масштаба под печать.

### 2.5. Вложения

- Файлы на устройстве и на связи: фото шкафа, паспорт, скан схемы.
- Хранение: локальный том или S3-совместимое (согласовать), ограничение
  размера/типов, вирус-скан вне зоны ответственности.

## Этап 3. Расширение модели данных

Требует отдельного согласования — меняет ядро.

### 3.1. Пассивная инфраструктура `[раздел 3.1 аудита]`

Сейчас связь = «порт ↔ порт». Реальная линия проходит через патч-панели и
розетки. Варианты:

- **A (минимальный):** патч-панель заводится как обычное устройство с
  портами; линия «станок → розетка → панель → коммутатор» описывается
  цепочкой связей. Плюс: ничего менять не надо. Минус: на схеме связей
  появляются лишние узлы, «кто с кем реально общается» не видно.
- **B (полный):** новая сущность «кабельная трасса/линия» (`circuit`),
  объединяющая несколько сегментов; схема умеет схлопывать пассивные узлы.
  Плюс: и физика, и логика видны. Минус: заметная переработка модели, API и схемы.

**Рекомендация:** A на первом шаге (нулевая цена, работает уже сейчас,
достаточно добавить признак «пассивное устройство» у типа и опцию
«схлопывать пассивные узлы» на схеме), B — если практика покажет нехватку.

### 3.2. Стойки и шкафы

- Справочник стоек (название, высота в юнитах, расположение).
- У устройства: стойка, начальный юнит, высота в юнитах (в шаблоне).
- Экран «вид стойки» спереди/сзади.

### 3.3. IPAM

- Подсети (иерархия), связь VLAN ↔ подсеть.
- Проверка конфликтов IP и попадания адреса в подсеть.
- Отчёт «занятые/свободные адреса подсети».

## Этап 4. Автоматизация (опционально)

### 4.1. SNMP/LLDP-опрос

Поля в БД (`links.source`, `confirmed`, `last_seen_at`) уже заведены.

- Фоновый воркер, опрос коммутаторов по расписанию.
- Обнаруженные связи создаются с `source='lldp'`, `confirmed=false`.
- Экран «Расхождения»: что нашлось в сети, но не задокументировано, и
  наоборот; подтверждение/отклонение оператором.
- Учётные данные SNMP — в отдельном защищённом хранилище, не в БД открыто.

### 4.2. Развёртывание `[E3]`

- `Dockerfile` для фронтенда (build → nginx), общий `docker-compose.yml`
  на весь стек, фронт и API за одним origin (снимает вопрос CORS и ввод
  адреса API руками).
- Адрес API берётся из сборки/относительного пути, поле на экране входа —
  убрать или спрятать в «дополнительно».
- Healthcheck бэкенда в compose, политика рестарта, том для вложений.
- Резервное копирование БД: скрипт + инструкция в README.

## Вопросы к согласованию

1. Сколько устройств планируется реально (сотни / тысячи)? От этого зависит
   объём работ этапа 1.
2. Система только во внутренней сети или доступна снаружи? Влияет на глубину
   этапа 0 (2FA, аудит входов, срок сессии).
3. Патч-панели: вариант A или B (см. 3.1)?
4. Экспорт — какие именно формы нужны «на бумаге» (спецификация, кабельный
   журнал, схема)? Есть ли утверждённый шаблон в организации?
5. Нужен ли многопользовательский одновременный режим (оптимистичная
   блокировка, 1.6) или достаточно «последний сохранил — тот и прав»?
6. Планируется ли SNMP-опрос в обозримом будущем, или поля `source`/`confirmed`
   стоит убрать из UI до тех пор?
