# WireMap — аудит текущего состояния

Дата: 2026-08-07. Ревизия: `b8b54cb`.
Объём кода: ~7.3k строк (backend ~1.5k, frontend ~2.6k, ванильный прототип ~1.8k, SQL/доки ~1.4k).

## 1. Что есть сейчас

**Назначение.** Документирование физической сети предприятия: спецификация
оборудования, порты, кабельные связи, схема связей.

**Стек.**
- Backend: FastAPI 0.115 + SQLAlchemy 2.0 + PostgreSQL 16, JWT (python-jose),
  Argon2id. Запуск через docker compose.
- Frontend: React 19 + TypeScript + Vite 8, Mantine 9, TanStack Query 5,
  React Flow (`@xyflow/react`) для топологии, React Router 7.
- `frontend-vanilla-prototype/` — одноразовый прототип, заменён React-версией.

**Модель данных.**

```
device_types (категория + префикс кода)
  └─ device_templates (модель техники)   ── device_template_interfaces (порты модели)
       └─ devices (экземпляр в спецификации, code генерируется: SW-0001)
            ├─ interfaces (копируются из шаблона)
            │     └─ links (interface_a ↔ interface_b, 1:1 на порт)
            │           └─ link_templates (среда/кабель/цвет/стиль линии)
            ├─ device_tags → tags (вложенные, M2M)
            └─ topology_group_id → topology_groups (ровно одна, для рамки на схеме)
vlans, users, code_sequences, audit_log
```

Решения, которые считаю удачными и трогать не надо:
- статус порта (свободен/подключён) нигде не хранится — вычисляется по наличию
  записи в `links` (`serialize.py`), рассинхрона быть не может;
- коды устройств выдаются атомарно через `INSERT ... ON CONFLICT` (`codegen.py`),
  без гонки «найти максимум и прибавить»;
- теги (многие, вложенные) и группа на топологии (ровно одна) разделены —
  это разные по смыслу вещи;
- позиции узлов схемы хранятся в БД, «замороженные» узлы не пересчитываются.

**Роли.** `admin` (всё + пользователи), `editor` (правка), `viewer` (чтение).

## 2. Найденные проблемы

Приоритет: **P0** — чинить до продуктива, **P1** — до роста объёма данных,
**P2** — качество/удобство.

## 3. Чего в продукте нет как класса

Функциональные пробелы, важные именно для документирования заводской сети:

1. **Пассивная инфраструктура.** Связь строго «порт ↔ порт». Патч-панелей,
   кроссов, розеток, кабельных трасс нет — реальная линия «коммутатор → патч-панель
   → розетка в цеху → станок» задокументировать невозможно, только сквозным
   упрощением.
2. **Стойки и шкафы.** `location` — свободный текст. Нет юнитов, нет вида стойки.
3. **IPAM.** VLAN есть, подсетей/пулов/проверки конфликтов IP нет.
4. **Экспорт.** Ни спецификации оборудования в XLSX, ни кабельного журнала,
   ни схемы в PNG/SVG/PDF. Для передачи подрядчику/в архив — критично.
5. **Импорт.** Первичное наполнение возможно только руками через UI.
6. **История изменений** — данные пишутся, экрана нет (см. D4).
7. **Вложения** — фото шкафа, паспорт устройства, скан схемы.
8. **Создание связи на схеме** — `onConnect` не подключён, тянуть кабель
   мышкой между узлами нельзя.
9. **Карточка устройства по URL** — нет ссылки на конкретное устройство,
   всё живёт в одном списке с раскрывающимися карточками.
10. **Опрос SNMP/LLDP** — в README числится как «дальнейший шаг», поля в БД
    под него уже есть.
